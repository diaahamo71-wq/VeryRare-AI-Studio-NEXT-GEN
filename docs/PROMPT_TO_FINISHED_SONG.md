# Prompt-to-Finished-Song Engineering Plan

Status: design contract for implementation. This document is not a claim that every stage is already implemented.

## Product goal

A user provides a vocal recording and an instrumental, describes the desired result in natural language, and receives a finished song plus an honest engineering report. The experience should feel like working with a careful mix engineer: inspect the material first, explain the plan, make controlled changes, render a preview, run checks, and export only after the pipeline succeeds.

## Non-negotiable rules

1. **No random settings.** Every parameter must be tied to a measurable input feature, a specific phrase in the user's brief, a documented genre preset, or an explicit user override.
2. **Never invent capabilities.** A requested operation must be implemented by a verified internal processor or compatible plugin. If not available, report it as unsupported instead of pretending it happened.
3. **Preserve the source.** Never overwrite input audio. Every render is a new version with a report and reproducible settings.
4. **Explain decisions.** Store the reason, input evidence, parameter bounds, and processor for each planned change.
5. **Protect the voice identity.** Do not apply voice conversion, pitch correction, formant shifting, or aggressive denoising unless the user explicitly requests it and the relevant engine is available.
6. **Fail visibly and safely.** Sample-rate mismatch, clipping, silence, corrupt files, unsupported formats, plugin failures, and missing dependencies must produce actionable messages.
7. **No false mastering claims.** Distinguish sample peak, true peak, integrated LUFS, loudness range, and streaming-target compliance. Only report metrics actually measured.
8. **Human approval at meaningful boundaries.** Show a plan and a preview before final export; keep A/B comparison available.

## Intended pipeline

### Stage 1 — Intake and preflight
- Accept vocal and instrumental files; record file hashes, format, sample rate, channels, duration, peak, RMS, and clipped-sample count.
- Check whether both tracks have compatible sample rates and whether their durations differ materially.
- Do not silently align musical timing, time-stretch, or resample. Explain proposed corrections and use explicit, tested operations.
- Warn if a file appears silent, clipped, too short, or unusually noisy. Do not label noise as a fact without a measurement.

### Stage 2 — Audio analysis
- Measure vocal and instrumental independently and together.
- Add tested estimates for silence, loudness over time, spectral balance, transient/peak behavior, and section boundaries.
- Mark estimates with confidence; avoid pretending simple RMS analysis understands lyrics, emotion, key, or arrangement.
- Keep original measurements so the final report can show before/after changes.

### Stage 3 — Convert the user's prompt into a constrained brief
- Extract goals such as intimate, dreamy, warm, dark, wide, dry, or spacious.
- Map each goal to a documented set of allowed processor choices and bounded parameter ranges.
- Resolve conflicts explicitly (for example, “very dry” and “huge reverb”). Ask a focused question only when a conflict materially changes the result; otherwise use the safer interpretation and disclose it.
- The prompt is not executable code. Never run code or shell commands generated by a model.
- Store the normalized brief, chosen preset, parameter values, and rationale as JSON so the same job can be reproduced.

### Stage 4 — Build an engineering plan
Each planned step must include:
- processor ID and implementation/version;
- target track or bus;
- parameters and hard safety bounds;
- reason tied to the brief or measured audio;
- expected effect and possible trade-off;
- whether the processor is installed and verified;
- whether the operation is reversible.

Unsupported steps remain visible as blocked items and cannot be silently skipped.

### Stage 5 — Preview and controlled processing
- Apply the plan non-destructively in a stable, documented order.
- Keep vocal and instrumental gain staging separate.
- Use conservative processing first; avoid adding effects simply because a preset normally contains them.
- Make reverb/delay tails and all processing transitions safe at file boundaries.
- Render a preview and let the user compare source, processed vocal, and full mix.
- Keep the exact settings used for each render.

### Stage 6 — Technical quality gates
Before a render can be called complete:
- confirm output exists, is finite, decodable, and has the expected sample rate/channel count;
- detect and report clipping and peak-ceiling violations;
- check for accidental silence, truncated tails, duration changes, and unexpected DC offset where implemented;
- verify all requested supported steps ran and identify all blocked/failed steps;
- run tests against deterministic synthetic fixtures and edge cases.
A passed technical check is not a guarantee of subjective quality; the report must say so.

### Stage 7 — Export and delivery
- Export a new high-quality WAV, the processed vocal, and a JSON engineering report; add stems only when they can be rendered reliably.
- Add optional delivery formats only after a tested conversion path exists.
- Report sample peak separately from LUFS/true peak. Do not claim streaming-ready loudness unless the correct meters and checks are implemented.
- Preserve a reproducible job record and never overwrite previous exports.

## Implementation sequence

1. Keep the current deterministic DSP mixer as the baseline and test it.
2. Add a strict, versioned job/plan schema and validation tests.
3. Add reliable preflight checks and clearer diagnostics.
4. Connect prompt interpretation to the plan schema; label local heuristics honestly and require explicit cloud consent for any cloud text processing.
5. Make the UI apply only validated settings and display the reasons before rendering.
6. Add preview/A-B and render quality gates.
7. Add verified advanced processors one at a time (for example, better reverb, loudness/true-peak metering, denoising, or pitch tools), each with tests and capability detection.
8. Verify the VST3 adapter with specific plugins and Windows tests before calling it production-ready.
9. Package and test on the target Windows machine only after the audio pipeline is stable.

## Acceptance criteria for “one prompt → finished song”

This milestone is not complete until all of these are true:
- one prompt plus the two source files can start a job without manual slider editing;
- the normalized plan is visible and reproducible;
- every executed processor is real, detected, and reported;
- unsupported requests are clearly identified before export;
- a preview and A/B comparison are available;
- export produces a new high-quality audio file and report;
- automated tests cover normal inputs, mismatched sample rates, silence, clipping, corrupt inputs, and parameter bounds;
- the workflow passes CI and is manually verified on Windows with real audio.
